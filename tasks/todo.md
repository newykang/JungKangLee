# JungKangLee 작업 체크리스트

[150분 개발 계획](plan.md) · [API·UI 계약](api-contract.md) · [Vercel 및 QA 실행표](vercel-qa.md)

## 0–35분 · 공통 기반

- [ ] **A** 역할과 계약을 확정하고 Vercel Git 연결·Production 브랜치·평가자 접근을 확인한다.
- [ ] **B** 공식 출처로 검증한 샘플 한 건을 A에게 전달하고 나머지 데이터를 준비한다.
- [ ] **C** 계약 예시로 모바일 카드, 출처 링크, 로딩·빈 상태·실패 화면 초안을 만든다.
- [ ] **A** `feat/demo-base` Preview에서 `/`의 카드 한 건과 같은 호스트의 `/api/updates` 응답을 확인한다. 동료 검토 후 병합하고 Production URL과 소스 SHA를 기록한다.

## 35–110분 · 세 역할 병렬 구현

- [ ] **A · `feat/frontend`** 상대 URL로 API를 호출하고 UI에 전달한다. 선택한 앱만 표시하고, 새로고침 후 선택을 복원한다. 전부 해제하면 전체 보기로 돌아간다. HTTP 오류 또는 네트워크 실패 후 재시도가 동작한다.
- [ ] **B · `feat/backend`** 앱 3개, 릴리스 4건 이상과 한 앱의 버전 이력을 포함한다. 공식 출처·고유 ID·패키지 참조·날짜·서버 정렬을 대조한다. Preview에서 계약의 `200`, `405`와 빈 데이터 응답을 확인하고, 실패 응답은 로컬의 테스트 데이터로 확인한다.
- [ ] **C · `feat/ui`** 카드의 요약·날짜·출처·샘플 표시와 네 가지 화면 상태를 구현한다. 390px 너비와 데스크톱에서 레이아웃을 확인하고 키보드로 필터와 링크를 조작한다.
- [ ] **A/B/C** 각 PR에 변경 경로, 테스트 방법과 결과, Preview URL 및 SHA를 남긴다. A가 B의 PR, B가 C의 PR, C가 A의 PR을 검토한다. A가 준비된 PR을 순차 병합하고 110분에 기능을 동결한다.

## 110–150분 · 평가와 시연

- [ ] **A** 평가자 조건으로 Production URL을 열고 Vercel 배포 SHA를 확인한다. 브라우저 네트워크에서 같은 호스트의 `GET /api/updates`가 `200`을 반환하는지 확인한다.
- [ ] **C** 모바일·데스크톱에서 관심 앱 선택 → 새로고침 → 공식 출처 → 전체 보기 경로를 검증한다.
- [ ] **B** API 기록과 화면을 공식 출처에 대조한다. **C**는 `tasks/qa-results.md`에 URL, QA한 배포 SHA, 확인 시각, 항목별 판정과 결함을 남긴다.
- [ ] **A/B/C** 최종 URL로 리허설한다. 새 배포가 지연되면 검증된 이전 Vercel URL과 해당 기능 범위를 공유한다.
